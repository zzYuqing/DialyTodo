# 复合任务（Complex Task）设计

> 阶段 7 功能。定位：**基于一次性长期任务的「父子任务」结构**。
> 本期范围收窄：不做子任务的独立提醒、不做按日期的子任务过滤、不改完成率口径。

## 一、目标与范围

用户原始需求：

1. 复合任务基于一次性长期任务，可有截止日（DDL），也可无截止日；
2. 可包含多条小任务（子任务），小任务可有截止日，也可没有；
3. 父任务带 DDL 时，子任务必须有 DDL；
4. 点「＋」创建时可选「单条任务 / 复合任务」，前者沿用现有功能；
5. 复合任务显示在长期任务页，默认显示大标题与基本信息，可展开看子任务；
6. 子任务可单独勾选完成；
7. 能看到整个复合任务的完成进度。

经讨论补充并已确认的规则（本次决策记录见第九节）：

8. 父任务的圆形勾选按钮**不可点**，完成状态由子任务推导（见第四节）；
9. 完成率 / 贡献墙：复合任务按 **1 条**计，`DayCompletion` 语义不变；
10. 日清单同样显示复合任务（它天然每天出现），展开规则见第六节；
11. 子任务顺序**持久化且不按日期隔离**：某天拖过顺序，后续任何日期打开都是这个顺序；
12. 编辑父截止日收敛时，越界的子任务截止日**自动裁剪并提示**；
13. 子任务字段保留 `title + note + dueDate`；
14. 数据兼容策略：**可选字段 + normalize 补齐，不改版本号**（见第七节）；
15. **子任务是完整的 Task**（有独立 id、进扁平 `Task[]`、进 tasks.json），
    但**子任务自身不存任何父指针**；父子关系唯一真相源是父任务的 `children: string[]`，
    **数组顺序即显示顺序**（详见第二节）；
16. **周期性任务不能作为子任务**，且**只支持两级**（复合任务里不再嵌复合任务）。

**明确不做**（本期）：子任务独立提醒、子任务单独归档、按「今天到期」过滤子任务、父圆圈的批量操作、
把已存在的普通任务拉进任务集（`attachSubtask` 的能力本期先备好，入口留到后续，见第十节）、
复合 → 单条的逆向转换。

## 二、数据模型

### 2.1 子任务是独立 Task，不是内嵌结构

曾考虑把子任务设计为内嵌的 `SubTask` 结构（嵌在父任务里），**已否决**。理由：

- 用户明确要支持「把已存在的普通一次性任务拉进任务集」。内嵌方案下这一步只能"销毁原 Task → 重建 SubTask"，
  id 变了、 `instances` 历史与创建时间丢了，迁移不干净；
- 独立 Task 下这只是一个 `attachSubtask` 调用（把 id 追加进 `children`），幂等、可逆、零数据损失；
- 代价是不能享受「内嵌自动连带归档」的红利，必须显式写连带逻辑（见第八节第 5、8 条）。
  这是本方案唯一多出来的代码量，换来的是可迁移性，值得。

### 2.2 关系存法：双向存，但只有一处真相源

```ts
Task {
  id: "parent-uuid",
  kind: "composite",
  children: ["childA", "childB"],      // ← 权威源：成员 + 顺序
  ...
}
Task { id: "childA", kind: "single", parentId: "parent-uuid", childDoneAt: "..." }  // ← 派生索引
Task { id: "childB", kind: "single", parentId: "parent-uuid", childDoneAt: null }
Task { id: "childC", kind: "single", parentId: null,          childDoneAt: null }   // 普通任务
```

**两侧都存，但不是两个真相源 —— 是「权威源 + 派生索引」：**

| | 角色 | 谁写它 |
| --- | --- | --- |
| 父的 `children: string[]` | **权威源**，表达成员 + 顺序 | 唯一的写入口（`composite.ts` 的那几个函数） |
| 子的 `parentId: string \| null` | **派生索引**，仅供 O(1) 读取 | 由 `syncChildrenIndex` 从 `children` 全量重建，写入时顺带给 |

**为什么是这个方向（`children` → `parentId`）而不是反过来**：
顺序只存在于 `children`，所以 `children` 必须是权威方。反过来从 `parentId` 重建 `children`
虽然也能算出成员，但**拿不回顺序** —— 那等于把用户的拖拽结果丢掉。所以方向只能是这个。

**每次载入 / 导入合并后跑一次 `syncChildrenIndex`，以 `children` 为准全量重建 `parentId`：**

```ts
/**
 * 以 children 为准，全量重建每一条任务的 parentId。
 * 挂在载入与导入合并之后，跑完之后内存里两份数据保证一致。
 *
 * 三步：
 *   1. 每个 composite 的 children 过滤掉「指向不存在任务」的幽灵 id（保序）；
 *   2. 按 children 建 (childId -> parentId) 映射；
 *   3. 全表每条任务写 parentId = 映射值 ?? null。
 *
 * 这是「全覆盖」的重建，因此任何中途的对不上都会被自愈，而不是累积成脏数据。
 */
syncChildrenIndex(tasks: Task[]): Task[];
```

这么做以后，**之前那套悬空分析仍然完全成立**，代价没有回来：

| 异常 | 重建后的结果 |
| --- | --- |
| `children` 里有幽灵 id | 幽灵被过滤 → 没有个别任务指向脏数据 |
| 父任务被硬删 | 没有任何 `children` 收录它 → `parentId` 重建为 `null` → **降级回普通顶层任务** |
| `parentId` 指向不存在的父 | 第 3 步被覆盖，不可能残留 |

也就是说：**拿到 O(1) 的读取便利，但失效模式仍然是「降级」，不是「静默消失」。**
最坏情况不是数据错乱，而是「当次会话内存里短暂对不上，重载即自愈」。

**为什么不要 `hasParent: boolean`（已否决的旧提案）**：那个布尔和 `parentId` 表达的是同一件事，
但前者无法指出「父是谁」，且与 `children` 冲突时会造成**同一个任务显示两次**
（顶层一次 + 父展开区一次），而 `parentId` 可以 self-heal。`parentId: null` 已经完整表达了「无父」。

**真正的性能账**（顺手纠正一个猜测）：这个性能顾虑其实并不存在——
建一个几百元素的 Set／Map 只要几十微秒，而 React 一帧里的 DOM 工作比它大几千倍。
真正值得担心的**不是"判断顶层"**，而是 **`childTasksOf` 被每个父任务调用一次会变成 O(n·m)** ——
这个用「进入列表循环前 `useMemo` 建一次 `Map<id, Task>`」解决即可（见 2.4）。

### 2.3 Task 新增三个可选字段

```ts
// src/types/task.ts 追加（既有字段一个不动）

export interface Task {
  // ... 既有字段不变 ...

  /**
   * 任务形态。缺失视为 "single"，由 normalizeTask 补齐。
   * kind 只在存储层与 formData 层出现，UI 判定一律走 isComposite()，不裸比较字符串。
   * 显式存它（而不是用 children 的存在性推导）的唯一理由：表达「零子任务的空任务集」，
   * 且表单开关 / 长期行展开区 / 校验都依赖这个显式概念。
   */
  kind?: "single" | "composite";

  /**
   * 子任务 id 列表，**数组顺序即显示顺序**。
   *
   * 这是父子关系的**权威源**：成员与顺序都只存在这里（理由见 2.2）。
   * invariant（由 normalizeTask 与 composite.ts 的写入函数共同保证）：
   *   - kind === "composite"  → children 必为数组（空数组 = 还没加子任务的空任务集）
   *   - kind !== "composite"  → children 归一为 undefined
   *   - 同一个 childId 只能出现在一个 composite 的 children 里（attachSubtask 保证）
   *   - children 里不出现「任务集」自身的 id，也不出现另一个 composite 的 id（只两级）
   */
  children?: string[];

  /**
   * 所属任务集的 id；**顶层任务恒为 null**（这个 null 就是「我是普通任务」的标记）。
   *
   * 这是 children 的派生索引，不是独立的第二份关系数据 ——
   * 唯一的生产者是 syncChildrenIndex（载入 / 导入时全量重建）与那几个关系写入函数。
   * 存在它纯粹为了让「是不是顶层」「属于哪个父」变成 O(1) 读取，避免到处传 Set。
   * 好处是所有不一致都能在下次载入时被自愈，而不是累积成脏数据。
   */
  parentId?: string | null;

  /**
   * 作为子任务时的完成时刻（ISO8601），未完成为 null。顶层任务恒为 null。
   *
   * 为什么不复用 completedAt：completedAt 的定义是「跨天一次性长期任务的永久完成日期」
   * （lib/ddl.ts 的 isLongTermOnce 要求 endDate !== startDate），会把单日子任务判为"不该有"，
   * 而且它会驱动 occursOn 关闭未来日期——子任务的展示不走那条链路，写它只会造成语义打架。
   * 用独立字段，子任务的 instances / completedAt 恒保持不变（空 / null），互不干扰。
   */
  childDoneAt?: string | null;
}
```

**子任务（收录者）的字段约束**：

| Task 字段 | 子任务取值 | 说明 |
| --- | --- | --- |
| `parentId` | 父任务 id | 由 `attachSubtask` 写入、`syncChildrenIndex` 重建。`null` = 普通顶层任务 |
| `schedule.type` | 恒 `"once"` | 周期性任务禁止进集（规则 16） |
| `schedule.startDate` | ≥ 父 `startDate` | 表单默认取父 `startDate`，允许改晚 |
| `schedule.endDate` | 子任务截止日，可 `null` | 受父区间约束，见第三节 |
| `completedAt` | 恒 `null` | 子任务不走那套完成链路，永远不用它 |
| `instances` | 恒 `{}` | 同上；保持为空，避免伪造出历史完成记录 |
| `archived` | 平时 `false` | 父任务归档时连带置 `true`（见第八节第 5 条） |
| `childDoneAt` | 完成时刻 / `null` | **子任务唯一的完成状态来源** |

子任务之所以让 `instances` / `completedAt` 全程保持"空"：它被收录后不进
`collectTasksOfDay` 的顶层过滤，自然不参与完成率、贡献墙、DDL 提示、
`hideCompleted` 这些既有链路——不需要为它们写任何额外过滤。

### 2.4 判定函数（children 权威，parentId 派生索引）

新增 `src/lib/composite.ts`（纯函数层，遵守 `lib/index.ts` 的约束：不得 import `@tauri-apps/*`、react、zustand）。

这一层的**读函数全是 O(1)** —— 因为每条任务带着 `parentId`，不必为了判断顶层与否去扫全表。
唯一需要注意的地方：**按 id 查实体**（而不是查关系）仍然要有 Map，否则每个父任务调一次
`childTasksOf` 会退化成 O(n·m)。做法是渲染层进入列表循环前 `useMemo` 建一次 Map，往下传。

```ts
// ── 身份判定（全部 O(1)）──
isComposite(task: Task): boolean;                // kind === "composite"
/** 是否是顶层任务：直接看 parentId，不需要任何 Set / Map */
isRootTask(task: Task): boolean;                 // task.parentId === null
/** 是否是某个任务集的成员 */
isSubtaskOf(task: Task): boolean;                // task.parentId !== null

// ── 按 id 查实体：统一走 Map，避免逐个 parent 扫全表 ──
/** id → task 的索引。渲染层在进入列表循环前建一次（useMemo），往下传 */
buildTaskMap(tasks: Task[]): Map<string, Task>;
/** 反向查父：直接读 task.parentId 后按 id 取一次性 O(1) */
findParentOf(map: Map<string, Task>, task: Task): Task | null;
/** 按 children 顺序返回子集实体；自动跳过指向不存在任务的幽灵 id */
childTasksOf(map: Map<string, Task>, parent: Task): Task[];

// ── 关系写入（幂等，返回新数组，不改原对象）──
/** 把 childId 加进任务集：先从所有其他任务集里摘掉，再同步双方的 children 与 parentId */
attachSubtask(tasks: Task[], parentId: string, childId: string): Task[];
/** 从任务集摘掉 childId：children 移除该项 + child.parentId 置 null，子任务随即恢复为普通任务 */
detachSubtask(tasks: Task[], parentId: string, childId: string): Task[];
/** 拖拽后写回顺序：按 orderedIds 重排该父的 children（顺序不变，parentId 无需改动） */
reorderSubtasks(tasks: Task[], parentId: string, orderedIds: string[]): Task[];
/** 归档任务集时连带给 children 置 archived（详见第八节第 5 条） */
archiveWithChildren(tasks: Task[], parentId: string): Task[];

// ── 载入 / 导入后的一次性自愈 ──
/** 以 children 为准全量重建 parentId，顺带清掉幽灵 id（含原先 pruneGhostChildren 的活） */
syncChildrenIndex(tasks: Task[]): Task[];

// ── 进度与展示 ──
subtaskProgressOf(map: Map<string, Task>, parent: Task): { done: number; total: number; ratio: number };
/**
 * 展示口径的排序：未完成的在前（保持 children 原序），
 * 已完成的恒沉底。与既有 sortUnfinishedTasks 的分区思路一致，但不需要 order 字段。
 */
sortSubtasksForDisplay(subtasks: Task[]): Task[];
subtaskUrgencyOf(child: Task, today: string): "overdue" | "today" | "soon" | "none" | null;
```

**写入方的双写纪律**：上面四个 `attach / detach / reorder / archive` 是全项目唯一允许碰 `children` 的地方，
必须同时维护另一侧的 `parentId`。其他地方一律不许直接改 `children` ——
万一将来有漏网之鱼也不会损坏数据，因为下次载入时 `syncChildrenIndex` 会把 `parentId` 重建回来。
（可以视情况加一条 dev 下的 console 断言兜一层。）

### 2.5 复合任务的硬性约束

`kind === "composite"` 的任务必须满足现有长期一次性任务的定义
（`isLongTermOnce`：`schedule.type === "once"` 且 `endDate !== startDate`，含 `endDate === null`）。
即复合任务**必须具备长期任务语义**，因而天然每天出现在日清单、靠 `completedAt` 关闭，
日清单 / 贡献墙 / 完成率 / 备份 / per-type 存储 / 提醒的既有链路全部不受影响。

子任务同样是 `type === "once"`，因此 dev 的 per-type 分组下父子同落在 `once.json`，不会跨文件。

## 三、DDL 规则

### 3.1 规则表

子任务的截止日存在 `schedule.endDate` 上，下面统称「子 `endDate`」。

| 父任务 | 子任务 `endDate` | 判定 |
| --- | --- | --- |
| `endDate === null`（无 DDL） | 可为 `null`，也可有值 | 有值时必须 ≥ 父 `startDate` |
| `endDate !== null`（有 DDL） | **必填** | 必须落在 `[父 startDate, 父 endDate]` 区间内 |

### 3.2 校验时机

统一在**表单提交时**做一次性校验（沿用 `EditTaskModal` 的 `endDateInvalid` / `weekdaysInvalid` 写法），
不合法则禁用提交按钮并给出行内错误文案：

- 「父任务设置了截止日，子任务必须设置截止日」
- 「子任务截止日不能早于整体起始日（YYYY-MM-DD）」
- 「子任务截止日不能超过整体截止日（YYYY-MM-DD）」
- 「请至少添加一条子任务」

运行时校验（`lib/validate.ts` 的 `isTask`）只做结构校验，不做业务区间校验 —— 避免把已经落盘的历史数据判成非法。

### 3.3 父截止日收敛时的自动裁剪（已确认）

编辑父任务把 `endDate` 提前时，所有 `endDate > 新 endDate` 的子任务在保存时自动裁剪到新的父 `endDate`，
并弹出提示（沿用现有浮层 / 弹窗形式），文案如：

> 已将 3 个子任务的截止日同步调整为 09-20（跟随整体截止日）

实现位置：`lib/composite.ts` 的纯函数

```ts
/** 把越界的子任务截止日收敛到父区间内，返回修改后的全表与受影响条数 */
clampSubtaskDueDates(
  tasks: Task[], parent: Task, parentStart: string, parentEnd: string | null,
): { tasks: Task[]; adjustedCount: number };
```

由 `EditTaskModal` 提交时调用；有调整则提示后再写入 store。

## 四、完成状态推导（核心）

### 4.1 唯一真相源 = 子任务群的 `childDoneAt`

```
children 里所有任务 childDoneAt !== null
   ├─ 父 completedAt = max(各 childDoneAt 的日期部分)
   └─ 父 instances[完成日] = { done: true, doneAt: nowIso() }   // 自动写入的那一条
任一子任务取消完成（childDoneAt 置 null）
   ├─ 父 completedAt = null
   └─ delete 父 instances[之前自动写入的那一天]
```

父任务的完成态**没有第二份状态**，全部由子任务群推导。这样做的好处是严丝合缝地复用既有语义：

- `occursOn` 读父 `completedAt` 关掉未来日期 ✓
- `isDoneOn` 读父 `instances` 显示历史完成 ✓
- 日清单「已完成区」沉底、`hideCompleted` 开关、贡献墙历史格子全部自动正确 ✓
- 子任务自身的 `instances` / `completedAt` 全程保持空 / null，与既有链路零交集 ✓

### 4.2 父圆圈不可点（已确认）

父任务的圆形勾选项**不提供交互**（`disabled` + 只读视觉：已完成时显示勾勾，未完成时显示空心圈）。
所有变化只能从子任务的勾选推进。理由：父圆圈无论做成「全选开关」还是「独立勾选」，
都会引入一套可能与子任务不一致的第二状态；只允许从子任务推进，语义最干净。

（推论：删除 / 取消最后一个已完成子任务时，父任务自动回到未完成状态，这是推导的自然结果，不做特殊提示。）

### 4.3 自动写入的 instances 记录与 toggleTaskDone 的关系

复合任务不复用 `toggleTaskDone`（它接受「某日 + done」的日维度入参）。
新增一组专门的函数，位于 `lib/composite.ts`：

```ts
/** 勾选/取消单个子任务（写 childDoneAt），并同步推导父任务的 completedAt 与 instances */
toggleSubtask(tasks: Task[], parentId: string, childId: string, done: boolean, nowIso: string): Task[];
/** 按 children 当前状态重算父任务完成态（新增/删除子任务、导入之后调用） */
deriveCompositeCompletion(tasks: Task[], parentId: string): Task[];
```

注意这里管理 instances 的口径：只维护「推导出的完成日」这一个键，不碰用户历史上
真实完成留下的数据 —— 目前复合任务的 instances 也只有自动写入这一种来源，两者不会打架。

## 五、完成率口径（已确认）

**复合任务按 1 条计**，`calcDayCompletion` / `calcDaysCompletion` / 贡献墙**一个字不改**。

理由：完成率表达的是「今天该做的事做了几件」，复合任务今天该做的事就是「推进这个复合任务」。
若按子任务展开计数，跨天推进的任务会让历史完成率与贡献墙色阶全部失真。

子任务进度只做**展示**：父任务行上加 `3/5` 徽标 + 一条细进度条。

## 六、UI 设计

### 6.1 新建 / 编辑表单（`EditTaskModal.tsx`）

顶部新增 **SegmentedControl：「单条任务 / 复合任务」**。不拆「＋」按钮。

- **单条模式**：现有表单，一字不改；
- **复合模式**：
  - 隐藏「周期」选择（固定 `once`），保留起始日期；
  - 「是否设置结束日期」保留，文案改为「是否设置整体截止日」；
  - 底部增加**子任务编辑区**：每行 = 标题输入 + 截止日输入 + 删除按钮，末尾「＋ 添加子任务」；
    - 「＋ 添加子任务」即创建一条新的独立 Task（`once`，`startDate` 默认取父 `startDate`），
      同时把它的 id 追加进父的 `children`；它立即出现在编辑区列表里，且不会进日清单顶层；
    - 新增行默认截止日 = 父 `endDate`（用户可改早）；
    - 父有 `endDate` 时截止日不可清空；
    - 至少 1 条子任务才能提交（与 weekly「至少选一天」同一口径）；
    - 子任务备注（`note`）在行内折叠式输入，第一步可与主备注同款的小输入框；
  - 校验与错误文案见 3.2。
- **编辑既有任务时**：
  - 复合任务禁止切回「单条」（会静默丢整套关系）→ 切换控件在编辑复合任务时禁用，并给出 hint；
  - 单条任务允许切到「复合」（保留原标题，子任务从 1 条起填）；
  - **打开一个子任务自身的编辑弹窗时**：它 `kind === "single"`、且有 `findParentOf` 命中，
    此时它是"被收录"的身份，应把日期类字段改为只读并给出「该子任务的截止日由所属任务集管理」的提示，
    避免用户在两个入口改同一份数据而绕过 3.1 的区间校验。（**待确认**：是改只读，还是允许改但在保存时
    同样走一遍区间校验。）

### 6.2 长期任务页（`LongTermView.tsx` + `LongTermTaskRow.tsx`）

三个分组（待完成 / 已逾期 / 已完成）照旧收录复合任务，归类沿用 `longTermBucket`（按父粒度判定）。

```
折叠态（行高与现有 LongTermTaskRow 保持一致）
▸ 写年度总结          [一次性] [起 09-01 → 止 09-30] [剩 15 天]
  ▁▁▁▁▁▁▁▁▃▃  3/5

展开态
▾ 写年度总结          [起 09-01 → 止 09-30] [剩 15 天]
  ▁▁▁▁▁▁▁▁▃▃  3/5
  ├ ☐ 收集素材                        止 09-10
  ├ ☑ 搭框架              09-05 完成
  ├ ☐ 写初稿    [今天截止]  止 09-15
  └ ☐ 排版校对                        无截止日
```

- 展开区数据来自 `childTasksOf(map, parent)` → `sortSubtasksForDisplay`，即直接按 `children` 顺序渲染；
  其中 `map` 是页面顶层的 `useMemo(() => buildTaskMap(tasks), [tasks])`；
- 展开/收起用 Chevron 图标按钮，行内区域展开（不做抽屉、不做二级弹窗）；
- 展开状态存组件内 `useState<Set<string>>`（按父任务 id），**不落盘**，避免污染数据结构。
  长期页与日清单各自独立维护展开状态。

### 6.3 日清单（`DayMode.tsx` / `SimpleModeView` + `TaskItem.tsx`）

复合任务每天出现（继承长期任务语义），折叠/展开交互与长期页一致。

**日清单顶层过滤（新增）**：`collectTasksOfDay` 的结果需要额外剔除被收录的任务，
否则同一个任务会既在顶层出现、又在父的展开区出现。因为每条任务自带 `parentId`，
过滤就是一行 `filter(isRootTask)`，**不需要 Set、不需要提前算 —— 也不可能因为漏传参数而失效**。

**展开范围（已确认）**：全部子任务都显示，不按日期过滤。排序规则：

- 未完成的在上（保持 `children` 原序）；
- 已完成的恒沉底、置灰、标题加删除线，不参与拖拽也不能作为放置目标。

**子任务拖拽排序（已确认）**：复用现有的 Pointer Events 拖拽实现（`DayMode.tsx` 的 `handleDragPointerDown`
已经解决了「点击/双击不被吞」「插入线」「只允许在未完成区放置」这些问题）。
顺序写回父任务的 `children` 数组（`reorderSubtasks`），**持久化到 tasks.json**。
因为顺序存在父任务上而非按日期存储，所以「某天拖过顺序后，之后任何日期打开都是这个顺序」天然成立，
无需额外处理。第一阶段先实现日清单里的子任务拖拽，长期页展开区第二步跟上（同一套 handle，抽出公共 hook）。

注：因为顺序就是数组下标，这里**不需要**子任务各自的 `order` 字段，也不走既有 `Task.order` 那套
「显示区整体固化 0..n-1」的逻辑——省掉的正是这一层转换。

### 6.4 简易模式（`SimpleModeView`）

复用同一个 TaskItem 行组件，只显示标题 + 进度徽标；展开规则同 6.3。

## 七、存储与兼容

**策略：可选字段 + `normalizeTask` 补齐，不改版本号。**

| 环节 | 是否要改 | 说明 |
| --- | --- | --- |
| `constants/storage.ts` 的 `CURRENT_VERSION` | 不改 | 保持 1 |
| `validate.ts` 的 `MIGRATIONS` | 不改 | 无迁移步骤 |
| `validate.ts` 的 `isTask` | **要改** | `kind` 存在时必须是两个字面量之一；`children` 存在时必须是字符串数组（元素只做 string 校验）；`parentId` 存在时必须是 string 或 null；`childDoneAt` 存在时必须是 ISO 串或 null |
| `validate.ts` 的 `normalizeTask` | **要改** | 补 `kind ?? "single"`；`kind === "composite"` 时 `children ?? []`，否则 children 归一为 `undefined`；`parentId ?? null`；`childDoneAt ?? null`。**不做跨任务的校验**（成员指向的任务是否真的存在、`children` 与 `parentId` 是否互相一致），那是 `syncChildrenIndex` 的活，需要全表上下文 |
| `parseTasksFileCompatible` / `parseTasksValueTolerant` | 不改 | 门槛不变 |
| 备份 / 导入导出 / `mergeTasks` | 不改 | 结构未变；但链路末端要跑一次 `syncChildrenIndex`，见下方「多跑一次自愈」 |
| dev per-type 分组（`saveTasksDev`） | 不改 | 父子都是 `type === "once"`，同落 `once.json` |
| `reminderService` | 不改 | 提醒只在父任务上，子任务不单独提醒 |

**新增的一致性动作：载入 / 导入后跑一次 `syncChildrenIndex`。**
因为子任务是独立条目，`children` 里的 id 有了「指向不存在的任务」的可能
（手工改文件、外部导入、跨分支 merged 等），而 `parentId` 是派生值、天然可能与之不同步。
因此在**载入任务后**与**导入合并后**各跑一次 `syncChildrenIndex(tasks)`，
与现有 `sortTasksByCreatedAt` 并列。它一次性完成两件事：清幽灵 id，以及重建全部 `parentId`。

关系的 invariant（2.3 那四条）建立在「一份全表」之上，所以这一步必须挂在**拿到全表之后**
的环节，`normalizeTask`（单条粒度）里管不了。反过来也一样：正因为入库前统一重建过，
运行期的读逻辑可以**无条件信任 `parentId`**，不用到处判空兜两头。

与既有 `completedAt`、`weekdays` 完全同口径：新增字段 → normalize 补齐 → 老文件一个字不动。
**因此对旧数据是只读兼容的，不存在不兼容旧版本的问题，用户无需备份或迁移。**

### 存储样本

```json
{
  "id": "parent-uuid",
  "kind": "composite",
  "title": "写年度总结",
  "note": "",
  "createdAt": "2026-09-01T10:00:00.000Z",
  "schedule": { "type": "once", "startDate": "2026-09-01", "endDate": "2026-09-30", "weekdays": [] },
  "instances": {},
  "reminder": { "enabled": false, "time": "09:00" },
  "archived": false,
  "completedAt": null,
  "order": null,
  "children": ["child-a-uuid", "child-b-uuid"]        // ← 权威源
}
```

```json
{
  "id": "child-a-uuid",
  "kind": "single",
  "title": "收集素材",
  "note": "",
  "createdAt": "2026-09-01T10:00:05.000Z",
  "schedule": { "type": "once", "startDate": "2026-09-01", "endDate": "2026-09-10", "weekdays": [] },
  "instances": {},
  "reminder": { "enabled": false, "time": "09:00" },
  "archived": false,
  "completedAt": null,
  "order": null,
  "parentId": "parent-uuid",                          // ← 派生自上面的 children
  "childDoneAt": "2026-09-05T11:20:00.000Z"
}
```

子任务与普通一次性任务**结构完全相同**，差别只有三点：`completedAt` / `instances` 恒为空、
`parentId` 非空（被某个 `children` 收录）。
这让「把它从任务集里摘出来（`detachSubtask`：从 `children` 移除 + `parentId` 置 null）
立刻变回普通任务」天然成立。

## 八、边界问题清单

| # | 边界 | 处理 |
| --- | --- | --- |
| 1 | 零子任务的复合任务 | 表单禁止提交（同 weekly 至少选一天）；已存在的空任务集允许保留，`children` 为 `[]` |
| 2 | 父已完成，又新增子任务 | 自动回落为未完成（`deriveCompositeCompletion`）：`completedAt` 清零，之前自动写入的那条 `instances` 一并删除；更早的历史完成记录不属于本次推导范围，不动 |
| 3 | 删除子任务导致全部剩余项都已完成 | 父保持已完成，`completedAt` 是历史事实，不改历史 |
| 4 | 未来日期（selectedDate > today） | 复合任务本身照常显示，但展开区的子任务勾框禁用、整区只读，沿用既有 `disabledDone` 语义（子任务是全局一次性状态，在未来日期不应被修改） |
| 5 | 归档 / 删除父任务 | **必须显式连带**（`archiveWithChildren`）。这是本方案相对内嵌版本的主要额外代码：父置 `archived = true` 时把 `children` 里所有任务一并置 `true`。否则子任务会因为"没有任何父收录它"而**自动降级成普通顶层任务重新冒到日清单里**——本方案的失效模式是"降级"而非"丢失"，所以结果是"多出任务"而不是"少了任务"，但同样要堵 |
| 6 | `children` 里存在幽灵 id | 渲染时 `childTasksOf` 跳过；载入 / 导入后 `syncChildrenIndex` 清洗掉，落盘保持干净 |
| 7 | 同一个 id 出现在两个父的 `children` | `attachSubtask` 写入前先从其他任务集摘掉，保证唯一归属；`syncChildrenIndex` 重建时若真撞上，取**第一个**（按 tasks 数组序）作为父，其余摘掉 |
| 8 | 删除单个子任务 | `detachSubtask` 摘掉关系（`children` 移除 + `parentId` 置 null）+ 连带归档该子任务（否则它会以普通任务身份复活在日清单）。三件事放同一个 action 里保证原子性 |
| 9 | 复合任务能否作为另一个的子任务 | 禁止（规则 16，两级封顶）。`attachSubtask` 写入前校验目标 `kind !== "composite"`，表单下拉也过滤掉 |
| 10 | 周期性任务能否作为子任务 | 禁止（规则 16）。理由：周期任务的 `instances` 是按天记的，与子任务「全局一次性」的 `childDoneAt` 语义冲突，且会让 dev per-type 分组把父子写到不同文件 |
| 11 | 父任务拖到日清单排序？ | 父任务仍参与日清单行拖拽（`Task.order`），与子任务内部拖拽互不影响（后者写的是 `children` 数组） |
| 12 | 复合 → 单条转换 | 编辑时禁止（第六节 6.1），防止静默丢关系 |
| 13 | 子任务全部完成当天 | 自动写入父 `instances[当天]`，当日完成率分母 1、分子 1 ✓ |
| 14 | 导入备份 / `mergeTasks` 之后 | 关系的两侧可能与父/子不在同一份数据里。合并后跑一次 `syncChildrenIndex` + `deriveCompositeCompletion`（对每个 composite）即可自愈：找不到父的一律降级为普通任务，不会消失 |
| 15 | 有代码绕过了收口，只改了 `children` 没同步 `parentId` | `syncChildrenIndex` 下次载入时全量重建 `parentId` 自愈。**代价要说清楚**：当次会话内该任务会暂时"两边都不显示"（`parentId` 非空被顶层过滤掉，又已不在 `children` 里）—— **重载即恢复**。这是本方案唯一存在的「暂时看不见」窗口，靠「写入只走 `composite.ts` 那四个函数」+ 可选的 dev 断言来堵 |
